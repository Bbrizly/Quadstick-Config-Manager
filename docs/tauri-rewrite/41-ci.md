# CI design

## Preserve current guarantees

Current CI:
- runs tests on PR/push;
- explicitly sets `QSCM_TELEMETRY=0`;
- uses least-privilege contents permissions;
- builds release platform matrix only for version tags;
- injects Google/PostHog secrets only for release build;
- publishes GitHub Release artifacts.

Target keeps these guarantees.

## PR workflow

### `legacy-dotnet`
Until retirement:
```bash
dotnet test QuadStick.sln --nologo -c Release
```

### `rust`
```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```
Do not include feature flags that intentionally require absent hardware unless fake-backed.

### `frontend`
```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm test --run
pnpm build:web
```

### `parity`
- build C# oracle/qsf;
- run canonical fixture export/differential tests;
- compare fixture manifest hashes;
- fail on unexplained golden change.

### `security`
- `cargo audit`/RustSec equivalent;
- JS dependency audit according to locked-tool policy;
- secret scanning existing platform;
- capability manifest static check: forbidden frontend plugin permissions absent.

### `accessibility`
- axe tests;
- pseudo-localization/RTL component smoke;
- keyboard critical-flow component tests.

## Platform build matrix

On PR or scheduled/nightly, at least compile/bundle check Windows/macOS/Linux so native adapters cannot rot. Expensive full release packaging may remain tag/manual.

## Tag release

Version tag triggers:
1. all required tests;
2. platform Tauri bundle;
3. code signing/notarization per platform;
4. Tauri updater artifact/signature if updater enabled;
5. artifact smoke/verification;
6. GitHub Release notes/files.

## Secrets

Release jobs get only the secrets they need. Google credentials go only to jobs that build feature-enabled release; updater signing key only signing step; Apple/Windows signing secrets scoped per OS. Do not write secrets to source when a Tauri/build env mechanism can consume them safely; if generated compile-time config is used, validate and guarantee cleanup/artifact scanning.

## Nightly/scheduled

Useful scheduled jobs:
- dependency/security audit;
- fuzz smoke with time budget;
- Linux/Windows/macOS build matrix;
- no automatic network product telemetry.

## Hardware CI

Do not fake hardware coverage. If a dedicated physical runner exists later, mark hardware tests separate and non-fork-safe. Otherwise use a versioned manual checklist for release candidate.
